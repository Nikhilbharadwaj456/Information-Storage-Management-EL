# 1. PROJECT OVERVIEW

## 1.1 Project Description

StorageLab is an interactive software application that simulates and analyzes enterprise storage management concepts.

It allows users to configure RAID systems, simulate disk failures, understand disk performance, compare backup strategies and analyze storage replication.

The application uses mathematical models, algorithms and simulations to demonstrate how storage systems behave under different configurations and operating conditions.

It does not require physical disks, RAID controllers, NAS/SAN devices or cloud infrastructure.

## 1.2 Problem Statement

Enterprise storage systems must provide high availability, reliability, performance and data protection.

However, understanding the behavior of storage configurations, disk failures, performance bottlenecks and backup strategies can be difficult without practical demonstrations.

StorageLab addresses this problem by providing an interactive environment where users can experiment with different storage configurations and observe their effects.

## 1.3 Project Objectives

1. Simulate different RAID configurations and evaluate their storage efficiency and fault tolerance.
2. Demonstrate disk failure, parity-based recovery and rebuild operations.
3. Analyze disk performance using fundamental storage performance equations.
4. Compare full, incremental and differential backup strategies.
5. Evaluate backup strategies against Recovery Point Objective (RPO) and Recovery Time Objective (RTO).
6. Demonstrate synchronous and asynchronous replication.
7. Provide interactive visualizations, comparison tables and performance graphs.

## 1.4 Scope

The project consists of three mandatory modules and two optional modules.

| Module | Description                      | Priority  |
| ------ | -------------------------------- | --------- |
| 1      | RAID Simulator                   | Mandatory |
| 2      | Disk Performance Analyzer        | Mandatory |
| 3      | Backup Strategy Planner          | Mandatory |
| 4      | Replication Simulator            | Optional  |
| 5      | Storage Security/Risk Assessment | Optional  |

The first three modules constitute the minimum complete project.

# 4. MODULE 1 – RAID SIMULATOR

**Syllabus mapping:** Unit II\
**Priority:** Mandatory\
**Responsible team member:** Person A

## 4.1 Objective

Simulate RAID configurations and demonstrate their capacity, performance characteristics, fault tolerance and recovery behavior.

## 4.2 User Inputs

The interface must accept:

1. RAID level: RAID 0, RAID 1, RAID 5, RAID 6 or RAID 10.
2. Number of disks.
3. Capacity per disk.
4. Optional disk read/write speed.
5. Disk to be failed during simulation.
6. Optional hot spare configuration.

## 4.3 RAID Levels to Implement

### RAID 0 – Striping

- Data is distributed across multiple disks.
- No redundancy.
- High parallel read/write potential.
- Failure of any disk results in array data loss.

Capacity:

Usable Capacity = N × S

Fault tolerance = 0 disks.

### RAID 1 – Mirroring

- Identical data is stored on mirrored disks.
- Provides redundancy.
- Read requests can be distributed across mirror copies.
- Write operations must update both copies.

For N disks arranged in two-way mirrors:

Usable Capacity = (N / 2) × S

Assume an even number of disks.

Fault tolerance depends on mirror-group failures.

### RAID 5 – Striping with Distributed Parity

- Data and parity are distributed across disks.
- Can tolerate one disk failure.
- Missing data can be reconstructed using XOR parity.

Usable Capacity = (N - 1) × S

Minimum disks = 3.

### RAID 6 – Striping with Dual Distributed Parity

- Stores two independent parity blocks.
- Can tolerate two simultaneous disk failures.
- Provides greater fault tolerance than RAID 5.

Usable Capacity = (N - 2) × S

Minimum disks = 4.

### RAID 10 – Mirroring + Striping

- Combines RAID 1 and RAID 0.
- Data is striped across mirrored disk pairs.
- Provides good performance and redundancy.

Usable Capacity = (N / 2) × S

Minimum disks = 4, with an even number of disks.

Fault tolerance depends on which mirror pairs lose their disks. It can tolerate multiple failures if they occur in different mirror pairs.

## 4.4 Required Outputs

For every RAID configuration, display:

- Raw storage capacity.
- Usable storage capacity.
- Storage efficiency.
- Fault tolerance.
- Read performance characteristics.
- Write performance characteristics.
- RAID disk layout.

Storage efficiency:

Efficiency = (Usable Capacity / Raw Capacity) × 100

Read/write performance should be represented using relative estimates or qualitative comparisons, not claimed as actual hardware benchmark measurements.

## 4.5 RAID Comparison

Display a comparison table:

| RAID    | Capacity  | Fault Tolerance  | Main Characteristic      |
| ------- | --------- | ---------------- | ------------------------ |
| RAID 0  | N × S     | None             | Performance              |
| RAID 1  | N × S / 2 | Mirror-dependent | Redundancy               |
| RAID 5  | (N-1) × S | 1 disk           | Balanced                 |
| RAID 6  | (N-2) × S | 2 disks          | Higher redundancy        |
| RAID 10 | N × S / 2 | Mirror-dependent | Performance + redundancy |

Also provide a chart comparing storage efficiency.

## 4.6 Disk Layout Visualization

Represent each physical disk as a column and each stripe as a row.

For RAID 5 with four disks, use an illustrative layout:

| Stripe | Disk 1 | Disk 2 | Disk 3 | Disk 4 |
| ------ | ------ | ------ | ------ | ------ |
| 1      | A1     | A2     | A3     | P1     |
| 2      | B1     | B2     | P2     | B3     |
| 3      | C1     | P3     | C2     | C3     |

P represents parity.

The visualization should clearly distinguish data blocks and parity blocks.

## 4.7 Disk Failure Simulation

Provide a disk selection dropdown and a button labelled "Fail Disk".

When clicked:

1. Mark the selected disk as FAILED.
2. Update the disk layout.
3. Determine whether the RAID array remains operational.
4. Display whether data is accessible.
5. Update the remaining fault tolerance.
6. Display the system state.

Possible states:

- Healthy.
- Degraded.
- Failed.
- Rebuilding.

The simulation must respect the failure characteristics of each RAID level.

## 4.8 XOR Parity Recovery

This is a major demonstration feature.

For RAID 5, demonstrate parity calculation using:

P = A XOR B XOR C

Example:

A = 1010\
B = 1100\
C = 0110

P = A XOR B XOR C

If C is lost:

C = P XOR A XOR B

Implement using Python's bitwise XOR operator (^).

The interface must:

1. Display original data blocks.
2. Calculate and display parity.
3. Allow one data block to be marked as missing.
4. Reconstruct the missing block.
5. Display the recovered value.
6. Verify that the recovered value matches the original.

Use a simple binary demonstration. This is a logical simulation, not a complete implementation of a production RAID controller.

## 4.9 Rebuild Estimation

Calculate approximate rebuild time:

Rebuild Time = Data to Rebuild / Rebuild Throughput

Display:

- Amount of data to rebuild.
- Rebuild throughput.
- Estimated rebuild time.

## 4.10 Hot Spare Simulation

Allow the user to designate an unused disk as a hot spare.

When an eligible disk fails:

1. Detect the failure.
2. Activate the hot spare.
3. Simulate reconstruction.
4. Show rebuilding status.
5. Mark the replacement as rebuilt after simulated completion.

Do not perform actual multi-terabyte data copying.

## 4.11 RAID Module Acceptance Criteria

The module is complete when:

- All five RAID levels calculate valid capacities.
- Invalid configurations are rejected.
- Storage efficiency is calculated correctly.
- Disk layout is displayed.
- Failure simulation works.
- RAID 5 XOR recovery is demonstrated.
- Rebuild time is calculated.
- Comparison table and graph are available.

# 5. MODULE 2 – DISK PERFORMANCE ANALYZER

**Syllabus mapping:** Unit I\
**Priority:** Mandatory\
**Responsible team member:** Person B

## 5.1 Objective

Analyze disk performance using fundamental disk performance equations and queueing principles.

The user must be able to modify disk parameters and observe how they affect response time, service time, IOPS and utilization.

## 5.2 User Inputs

Accept:

1. Disk RPM.
2. Average seek time (ms).
3. Transfer rate (MB/s).
4. Block size (KB).
5. Request arrival rate (IOPS).

Provide reasonable default values.

## 5.3 Required Calculations

### A. Average Rotational Latency

T_rotation = 30000 / RPM

Result is in milliseconds.

Example:

RPM = 7200

Average rotational latency = 30000 / 7200 = 4.167 ms.

### B. Transfer Time

T_transfer = Block Size / Transfer Rate

Use consistent units.

For example, convert block size from KB to MB before dividing by MB/s.

### C. Average Service Time

T_service = T_seek + T_rotation + T_transfer

Result is in milliseconds.

### D. Estimated IOPS

For a simplified single-request-at-a-time disk model:

IOPS = 1000 / T_service(ms)

This is a simplified service-capacity estimate, not a universal measure of actual hardware IOPS.

### E. Utilization

Utilization = Arrival Rate × Service Time

Convert service time into seconds before calculation.

U = λ × T_service(seconds)

Display utilization as a percentage.

The input arrival rate must not exceed the model's stable operating limit.

## 5.4 Little's Law

Implement Little's Law:

L = λ × W

Where:

- L = Average number of requests in the system.
- λ = Request arrival rate.
- W = Average response time.

Allow the user to modify arrival rate and display the average number of requests.

## 5.5 Response Time vs Utilization

Use the simplified M/M/1 queueing model.

Response Time:

W = T_service / (1 - U)

Here, service time and response time must use the same time unit.

Generate a graph:

- X-axis: Utilization (%).
- Y-axis: Average response time (ms).

Show the sharp increase in response time as utilization approaches 100%.

Do not calculate response time at or above 100% utilization because the stable queueing model is no longer valid.

## 5.6 Required Outputs

Display metric cards for:

1. Average rotational latency.
2. Transfer time.
3. Average service time.
4. Estimated IOPS.
5. Utilization.
6. Average response time.
7. Average number of requests.

## 5.7 Required Visualizations

- Response time vs utilization graph.
- IOPS comparison for different input configurations (optional).
- Performance interpretation.

Example interpretation:

"When utilization approaches 100%, requests spend increasingly more time waiting in the queue, causing response time to increase significantly."

## 5.8 Disk Performance Acceptance Criteria

The module is complete when:

- All disk performance calculations work.
- Unit conversions are correct.
- Little's Law is implemented.
- Utilization is calculated correctly.
- Response-time graph is generated.
- Invalid inputs and unstable utilization are handled.
- Results update when inputs change.

# 6. MODULE 3 – BACKUP STRATEGY PLANNER

**Syllabus mapping:** Unit IV\
**Priority:** Mandatory\
**Responsible team member:** Person C

## 6.1 Objective

Compare Full, Incremental and Differential backups based on storage requirements, backup duration and recovery complexity.

The module must also evaluate backup strategies against RPO and RTO requirements.

## 6.2 User Inputs

Accept:

1. Original data size (GB).
2. Daily data change percentage.
3. Retention period (days).
4. Backup throughput (MB/s).
5. Backup frequency.
6. Required RPO.
7. Required RTO.

## 6.3 Backup Methods

### A. Full Backup

Copies the entire dataset every time.

Advantages:

- Simple restoration.
- Independent recovery points.

Disadvantages:

- High storage consumption.
- Longer backup duration.

For R retained full backups:

Storage Required = R × D

### B. Incremental Backup

Copies changes since the immediately preceding backup.

Advantages:

- Low storage consumption.
- Shorter daily backup duration.

Disadvantages:

- Restoration requires the full backup and every subsequent incremental backup.

For one initial full backup and fixed daily changes:

Storage Required = D + (R - 1) × C

### C. Differential Backup

Copies changes since the last full backup.

Advantages:

- Faster restoration than incremental backups.
- Only one differential backup is needed along with the full backup.

Disadvantages:

- Differential backup size increases as more changes accumulate.

For fixed daily changes and one initial full backup:

Storage Required = D + C × [1 + 2 + ... + (R - 1)]

For this simplified model, cumulative differential size must be capped at the original dataset size.

Where:

D = Original data size.

C = Daily changed data.

R = Number of retained recovery points.

The application must state its simplified change-data assumptions.

## 6.4 Backup Duration

Backup Duration = Data Transferred / Backup Throughput

Ensure consistent units.

Calculate the backup window for each strategy.

## 6.5 Restoration Estimation

Full backup:

- Restore the required full backup.

Incremental backup:

- Restore the initial full backup.
- Apply every subsequent incremental backup in order.

Differential backup:

- Restore the initial full backup.
- Apply the latest differential backup.

Calculate approximate restoration time from the total data transferred.

Display the number of recovery steps and the amount of data restored.

## 6.6 RPO and RTO

RPO = Recovery Point Objective.

It represents the maximum acceptable amount of data loss, expressed as time.

RTO = Recovery Time Objective.

It represents the maximum acceptable time to restore the system.

Example:

RPO = 1 hour.

RTO = 2 hours.

A daily backup schedule cannot satisfy an RPO of one hour.

The application must compare:

- Backup interval against RPO.
- Estimated restoration time against RTO.

## 6.7 Recommendation Engine

Based on the inputs, recommend a suitable backup strategy.

Possible recommendations:

- Full backup for simpler recovery where storage capacity is sufficient.
- Incremental backup for reducing storage consumption.
- Differential backup for balancing storage and restoration complexity.
- Frequent backups where a lower RPO is required.
- Periodic full backups combined with incremental or differential backups.

If the selected configuration fails to meet RPO or RTO, explicitly display that it does not meet the requirements.

Do not recommend a strategy based solely on storage efficiency.

## 6.8 Required Outputs

Display:

- Storage required for each backup method.
- Backup duration.
- Restoration duration.
- Number of restoration steps.
- RPO compliance.
- RTO compliance.
- Recommended backup strategy.

## 6.9 Backup Module Acceptance Criteria

The module is complete when:

- All three backup methods are implemented.
- Storage requirements are calculated.
- Backup duration is calculated.
- Restoration requirements are explained.
- RPO and RTO are evaluated.
- Recommendations respond to user inputs.
- Comparison table and chart are available.

# 7. MODULE 4 – REPLICATION SIMULATOR

**Syllabus mapping:** Unit IV\
**Priority:** Optional

## 7.1 Objective

Demonstrate the differences between synchronous and asynchronous replication.

## 7.2 Inputs

- Replication mode.
- Network latency.
- Distance between sites.
- Local write processing time.
- Network bandwidth.
- Write frequency.

## 7.3 Synchronous Replication

The primary storage system waits for the remote acknowledgement before confirming a write.

Simplified model:

Write Response Time = Local Write Time + Network Round-Trip Time

## 7.4 Asynchronous Replication

The primary system acknowledges the local write without waiting for remote completion.

Simplified model:

Write Response Time ≈ Local Write Time

The remote copy may lag behind.

## 7.5 Outputs

- Write response time.
- Replication lag.
- Potential data loss window.
- RPO implications.
- Comparison of both replication approaches.

The model must clearly identify its assumptions regarding acknowledgement and network behavior.

- Incremental restoration should require more recovery steps than differential restoration.
- An insufficient backup interval should fail the RPO requirement.
- An excessive restoration time should fail the RTO requirement.
